# CareThread 一期架构合同

> 状态：2026-07-31 起生效。本文把用户新增范围、任务书红线与安全/性能/交互/对抗审查结论固化为实现约束。任何模块实现与本文冲突时，先修正实现或在本文记录经主 Agent 复核的替代方案。

## 1. 平台策略

- 一期是纯原生 iOS App：Swift、SwiftUI、SwiftData、Vision、VisionKit、UserNotifications、EventKit、LocalAuthentication。
- 不引入 Flutter、React Native、Kotlin Multiplatform 或 WebView 业务壳；不为二期 Android 牺牲 iOS 交互、无障碍、文件保护和系统能力。
- 为二期 Android 保留的是领域语义，而不是 UI 或数据库实现：稳定 UUID、明确枚举原始值、ISO 8601 时间与时区、规范单位、版本化 JSON/备份清单、可替换的 OCR/提醒/文件存储接口。
- Apple 特有标识只存在于适配层字段，例如通知 identifier、EventKit event identifier；核心业务记录不依赖其存在。

## 2. 本地成员是隔离边界

- 产品统一使用“成员/家人档案”，不把本地成员描述为登录用户；一期没有账号系统。
- `patientId: UUID` 是不可变租户键。记录、附件、指标、用药、医嘱、复查、提醒、导出任务、对比和审计均显式携带它。
- 所有查询必须先限定 `patientId`，然后再组合筛选；任何 service API 缺少成员参数或上下文都视为编译期/审查失败。
- 当前成员状态只保存 UUID；启动时校验仍存在。切换成员会提升 generation，取消旧查询、OCR 提交和分页结果。
- 拍照或导入开始时冻结 `capturedForPatientId`。处理中切换成员不能改变草稿归属。
- 成员上限由服务层原子执行：最多 20 人；第 21 人失败时不得写入数据库、目录或默认选择。
- 姓名不是主键。成员使用必填“档案称呼”、可选“报告上的姓名”和别名；同名成员合法。

## 3. OCR 姓名归属状态机

状态只有四种：

- `match`：规范化姓名命中当前成员的报告姓名或别名，可继续确认。
- `noEvidence`：OCR 没有可靠姓名证据，可继续，但必须提示人工核对。
- `mismatch`：可靠识别姓名与当前成员不一致，保存硬拒绝并提供切换成员。
- `ambiguous`：多姓名或多个同名成员，保存硬拒绝并要求明确选择。

`mismatch`/`ambiguous` 不提供普通“仍然添加”。只有用户主动点击“姓名识别可能有误”，阅读归属说明并二次确认后，才能以原冻结成员保存。每次决定追加不可变审计记录，至少包含草稿/记录/目标成员、检测姓名、状态、结果、覆盖原因、OCR 引擎与版本、时间。

闸门必须在保存服务执行，不能只靠 SwiftUI 按钮禁用。OCR 迟到结果、快速切成员、App 重启恢复草稿都要重新校验代次和冻结成员。

## 4. 数据语义与迁移

- 使用 `VersionedSchema` 与 `SchemaMigrationPlan`；即使 V1 尚未发布，也禁止继续依赖隐式默认容器。
- 数据库初始化或迁移失败时进入明确恢复态；不得静默删库重建。
- 用于筛选、排序、比较或关联的数据必须是正规化实体或稳定标量，不能埋在 transformable 数组/BLOB。
- OCR 原文、机器提取快照与用户确认值分层保存；机器重跑不能覆盖人工确认。
- 指标至少用 `(normalizedName, unit, eventDate, patientId)` 表达；不自动合并单位不同的值。
- 日期字段同时表达事件时间、精度与时区。事件年龄由成员出生日期和事件日期计算；出生日期缺失时必须返回未知而非猜测。
- 关键枚举使用稳定字符串 raw value；未知新值可降级展示，不因解码失败导致整库不可用。

### 4.1 内容编辑与修订

- “每个地方可编辑”指所有用户业务内容均有编辑入口，不代表系统不变量可被改写。稳定 UUID、`patientId`、不可变原件、SHA-256、原始 OCR 快照、归属审计、schema/备份版本只可由受控迁移或专用事务修改。
- 用户确认值与机器提取值使用不同字段；界面始终显示当前采用值及来源。重新 OCR 只追加机器快照，不回滚人工更正。
- 编辑服务以实体类型/id、冻结 `patientId`、期望 revision 和字段补丁为输入；校验成员范围与允许字段后，在同一 SwiftData 事务更新实体并追加内容修订。
- 修订至少记录 revision、变更字段键、可恢复的前后内容、来源、时间和本地操作者；敏感前后值只在受保护数据库中，不写入 OSLog、崩溃上报或公开测试附件。
- 撤销是一次新的追加修订，不删除历史。并发 revision 不匹配时拒绝覆盖并让用户重新载入。

## 5. 原件 Vault

- 唯一真实源是 `Application Support/Vault/v1/members/<patientId>/records/<recordId>/attachments/<attachmentId>/original.<ext>` 下的单份不可变原件。
- 文件名和目录不含成员姓名、医院或病历正文。数据库保存相对路径，不保存可迁移性差的绝对沙盒路径。
- 导入入口优先接收文件 URL 并流式处理；流程为 staging → 类型魔数/UTType/像素或页数检查 → SHA-256/字节数 → 原子 rename → 数据库提交。
- 同一目标已存在时必须校验摘要和大小；内容冲突不能被当作幂等成功。
- 缩略图、OCR 下采样图和 PDF 预览均为可重建派生物；不永久保留与原件等大的“工作副本”。
- 真实 Vault 不暴露给 Files。用户查看、复制、保存和分享的均是临时或 Documents 中明确标注的导出副本，外部修改不回写真实源。
- Vault、SwiftData SQLite/WAL/SHM、staging、导出临时目录和恢复日志使用 iOS Data Protection；锁屏不可用与文件缺失/损坏是不同错误。
- 真实 Vault 与数据库标记为排除 iCloud/系统备份，以满足医疗数据不写入 iCloud 的上架边界；不承诺 Quick Start 必然携带这些资料，正式迁移依赖附近同步或用户主动加密备份。
- 不加入 CloudKit、iCloud Documents、iCloud KVS 或相应 entitlement。Apple App Review Guidelines 5.1.3(ii) 禁止 App 在 iCloud 存储个人健康信息；这一约束高于“iCloud 同步更方便”的产品诉求。
- 导入拒绝视频时同时检查扩展名、UTType 与魔数；备份恢复拒绝绝对路径、`..`、符号链接/硬链接、重复规范化路径和压缩炸弹。
- 删除成员使用 journal 和受保护暂存区，支持崩溃后幂等继续；不能先删库再祈望文件删除成功。

## 6. 查询、筛选与分页

- 组合条件顺序固定为：成员 → 日期 → 病种/记录类型 → 医院 → 医生 → 事件年龄 → 排序。
- 日期筛选采用半开区间 `[startOfDay, startOfNextDay)`，避免日末精度和夏令时边界错误。
- 默认页大小 30，使用 keyset cursor，不使用 offset。
- 默认稳定顺序为 `eventDate DESC, createdAt DESC, id DESC`。其他排序同样必须追加稳定 UUID 作为最终 tie-breaker。
- Cursor 绑定 `patientId + canonicalFilterHash + sortVersion + lastTuple + dataGeneration`；成员、筛选、排序、插入、删除或恢复变化后旧游标明确失效。
- 每次 fetch 前后检查取消和 generation；旧成员或旧筛选结果不得回填当前列表。

## 7. OCR、高清图、PDF 与比较的资源约束

- OCR 以文件 URL 为入口，用 ImageIO 读取元数据并生成最长边约 4096 px 的 OCR 副本；原件不为 OCR 整图解码。
- Vision 由专用 actor 串行执行，默认并发 1；请求可取消，提交结果前复核 task generation。
- 高清预览采用系统可缩放查看和按需瓦片/下采样策略；关闭预览后释放解码图。
- PDF 使用 `UIGraphicsPDFRenderer.writePDF(to:)` 直接写受保护临时 URL，记录分批读取，图片只嵌入适合打印的下采样版本，分享传 URL。
- 本地比较按两个窗口分别查询，以 `(normalizedMetricName, unit)` 做线性配对；只输出数值与事实差异，不输出好坏、病因、风险或诊断建议。
- OCR、导出、比较和大文件操作不在 MainActor 执行；MainActor 只接收轻量 DTO 与 UI 状态。

## 8. 提醒与系统日历

- 本地通知与 EventKit 是两个独立适配器。权限拒绝、系统限制、日历被删除或用户取消都不能回滚病历保存。
- 每个业务提醒有稳定业务 UUID、成员 UUID、调度版本、通知 identifier 和可选日历 event identifier。
- 调度使用 replace/reconcile，重复保存不重复注册；修改和删除可重试且幂等。
- 待处理本地通知使用滚动窗口，不能为多年药物方案一次性铺满系统上限。
- 系统日历可能经 iCloud/第三方账户同步。UI 必须单独触发并说明，不能宣传为“完全本机”。

## 9. 导出、分享与恢复

- PDF 导出只覆盖一个成员，范围为近 1 月、6 月、1/2/5/10 年或全部；生成前后均复核 patientId 与过滤摘要。
- PDF 是阅读分享件，成员备份是含版本清单与哈希的恢复包；两者名称、入口与风险提示不得混用。
- 微信仅通过系统分享面板成为用户可选目标；不接微信 SDK，不写联网发送代码。
- 分享完成或取消后清理临时文件；启动时清理过期任务和临时文件。
- 导出/备份文案说明副本离开 App 后由目标位置负责保护。

## 10. iOS 附近同步与换机

- 唯一主线是 Apple 当前推荐的 `Network.framework + Bonjour + includePeerToPeer`；MultipeerConnectivity 已弃用，不进入新代码。
- App 没有互联网端点、服务器或账号；浏览、监听和点对点链路只在用户主动进入同步页面后开启，退出即停。
- 支持一个成员或全部成员的一致性快照。发现广播只含随机会话代号、协议版本和能力位，不含姓名、文件名或资料数量。
- 双方使用 P256 临时密钥、HKDF 和六位 SAS 配对码建立一次性信任；用户双端确认后，所有清单与文件分块使用 AEAD。
- 接收端在受保护 staging 校验版本、空间、成员上限、数量、引用、逐文件 SHA-256 和清单认证，通过后才事务提交。
- 相同 UUID + 相同哈希幂等跳过；不同内容绝不静默覆盖；一期不把删除传播到另一台设备。
- 分块流式传输，断线可从已验证偏移恢复；新连接重新协商会话密钥。取消、磁盘满、锁屏、版本不兼容和篡改不污染现有数据。
- AirDrop/系统分享只作为加密备份包的人工兜底，不代替可审计的 App 内同步流程。
- 自动化使用 in-memory/loopback transport 覆盖协议、故障和事务；无线发现、点对点链路、后台与网络切换最终以两台真机为准。

详细协议见 [`NEARBY_SYNC_DESIGN.md`](NEARBY_SYNC_DESIGN.md)。

### 10.1 iCloud 方案结论

- 本期结论是“不实现”，不是待决定事项。成员数据库、Vault、缩略图、OCR 文本、PDF 缓存和备份包不写入 App 自有 iCloud 容器。
- 系统日历条目可能随用户选择的日历账户同步，用户通过系统分享面板把导出副本保存到某个位置也属于用户主动动作；两者必须在 UI 中提示风险，不能宣传为 CareThread 云同步。
- 若 Apple 未来修改 5.1.3(ii)，只允许在重新完成审核规则、威胁模型、端到端加密、冲突合并和数据删除评估后开启新的产品决策，不预埋隐藏开关。

## 10.2 社区证据转化的本地能力

- “就诊准备卡”由用户确认的结构化字段、当前用药、过敏、诊断、医生、关键记录、问题清单和联系人组成；它是资料摘要，不是医生病历或医疗建议。
- “问医生的问题/就诊笔记”是成员限定的手动内容；不录音、不转写，不调用生成式模型。
- 补药提醒只使用用户输入的日期/时间和本地调度；不得根据药量、疾病或处方自行计算应服用方案。
- 本地全文搜索必须先限定 `patientId`，再搜索用户确认内容和 OCR 索引；结果仍受筛选、排序和 generation 约束。
- 重复检测使用文件哈希、感知/截图重叠信号，只显示建议；删除、合并和忽略必须由用户确认。

## 11. 自动化与性能门槛

最终数量下限仍为任务书的 ≥85 单测、≥16 UI 测、23 项边界矩阵、36 张真实模拟器截图；新增范围不能通过删减原测试换绿。实现目标提升到约 130 个单元/集成测试和 28 个 UI 测试。

P0 自动化必须覆盖：

- 20 人原子上限、同名成员、跨成员全链路零泄漏、切换中草稿冻结。
- 姓名四状态、迟到 OCR、二次确认与追加审计。
- 组合筛选、稳定游标、删除/插入中翻页、快速切换与 300+ 记录。
- Vault 摘要冲突、路径穿越、类型伪装、超大图、磁盘满、锁屏、崩溃恢复。
- 通知超限滚动调度、重复保存、权限变化、EventKit 失败。
- 七个导出范围、取消、临时文件清理、PDF 内容成员隔离。
- 指标缺失、单位不同、参考区间变化、低置信度和跨期事实比较。
- 标准版与长辈版同功能可达、动态字体、VoiceOver、Reduce Motion。
- 内容修订、撤销、不可变字段拒绝、跨成员编辑拒绝、就诊准备卡、问题清单、补药提醒、待整理收件箱、本地搜索和重要置顶。

暂定性能门槛以最低支持真机为最终口径，模拟器做相对回归：

| 场景 | 门槛 |
|---|---|
| 单成员 300 条组合筛选首屏 | 冷 P95 ≤250 ms，暖 P95 ≤100 ms |
| 加载更多/切成员 100 次 | P95 ≤150 ms，重复/跳项/跨成员均为 0 |
| OCR 12/48MP 输入 | 并发 1，峰值增量 ≤120 MiB，可在 500 ms 内取消 |
| Vault 25 MiB 图片/250 MiB PDF | 主线程阻塞 <50 ms，峰值增量 ≤32 MiB，永久存储 ≤原件 1.15 倍 |
| 300 条 PDF | P95 ≤15 s，峰值增量 ≤80 MiB，可在 500 ms 内取消 |
| 两个五年窗口本地比较 | P95 ≤300 ms，峰值增量 ≤25 MiB |
| 100 轮导入→OCR→预览→导出→删除 | 0 崩溃；第 100 轮 RSS ≤第 10 轮 +20 MiB |

## 12. 主 Agent 合入门禁

每个子任务返回后由主 Agent 执行：

1. 检查修改范围是否越界和是否覆盖他人改动。
2. 对照本文验证跨成员、离线、诊断红线和原生 iOS 策略。
3. 运行定向测试，再运行 `Scripts/verify.sh` 与 `Scripts/acceptance.sh`。
4. 更新 `IMPLEMENTATION_LOG.md`、`PROGRESS.md` 和 `BLOCKERS.md`。
5. 只提交已验证的同一里程碑文件；提交不含 `Co-Authored-By`。
6. 公开推送前扫描密钥、个人路径、真实医疗数据与依赖许可，并确认 GitHub 账号和仓库可见性。
